## SPEC-01：访问入口与账号开通合并

### 目标

- 内部用户首次登录无权限时，直接在无权限错误页内填写基本信息、选择角色、功能权限和数据权限并提交，不再先申请账号，也不跳转权限管理后台。
- 外部登录页不提供自助创建账号入口。
- 外部账号只能由内部关联人创建，并在创建流程内同步选择权限范围。

### 业务规则

1. 无权限页“申请访问权限”是导航入口，不在错误页创建独立申请单。
2. 错误页原地展示“基本信息、权限范围、提交申请”三步流程，预填当前内部 ITCode，不进入权限管理后台。
3. 基本信息只展示自动带出的申请人 ITCode、直线经理，以及选填的手机号、邮箱和申请原因。
4. 权限范围与系统内创建账号、权限变更保持一致，统一使用“添加角色、复制他人角色、选择数据权限”三个入口。
5. 所属租户支持多选；页面及权限选择弹窗内容超高时必须可以滚动到底部操作区。
6. 创建外部账号时，申请人即关联人；关联人字段自动带出且只读。
7. 创建账号流程必须保留权限范围步骤，提交一张包含账号资料和权限范围的申请。

### 不做

- 本阶段不调整最终审批节点顺序，由 SPEC-02 统一处理。
- 不接真实外部账号创建 API。

### 验收

- 对应 `P01-01` 至 `P01-03`。

## SPEC-02：身份化审批链路与审批摘要

### 目标

根据申请人/被申请人的内外部身份和是否本人申请，生成唯一且可解释的审批链。

### 审批矩阵

| 场景 | 审批链 |
| --- | --- |
| 内部用户为自己申请 | 申请人直线经理→全部业务负责人→系统自动生效 |
| 内部用户为其他内部用户申请 | 申请人直线经理→被申请人直线经理→全部业务负责人→系统自动生效 |
| 内部用户为外部用户申请 | 关联人（与申请人一致时省略）→申请人直线经理→全部业务负责人→系统自动生效 |
| 外部用户为自己申请 | 关联人→全部业务负责人→系统自动生效 |
| 外部用户为其他外部用户申请 | 被申请人关联人→全部业务负责人→系统自动生效 |

### 业务规则

1. 外部用户没有直线经理；被申请人为外部用户时，不展示也不生成“被申请人直线经理”。
2. 同一节点的关联人与申请人为同一人时，省略关联人节点。
3. 涉及多个业务负责人时并行等待，全部通过后整单一次性自动生效。
4. 普通权限变更不再生成系统管理员最终审批节点。
5. 系统管理员仅保留启用、禁用等实际操作或管理确认场景。
6. 申请人最终提交页只展示审批流；详细变更摘要放在审批列表/审批详情。

### 验收

- 对应 `P02-01` 至 `P02-05`。

## SPEC-03：复制权限与账号操作提单

### 目标

清楚区分“复制锁定范围”和“本次手工追加范围”，同时取消启禁用场景的手填单号。

### 业务规则

1. 复制对方当前有效的角色、由这些角色继承的功能权限与数据权限，以及用户单独授权的数据权限；用户级例外不包含功能权限。
2. 不复制租户、组织归属和账号资料。
3. 复制结果整体只读，不允许增加、删除、局部清除或修改来源。
4. “添加角色”“选择数据权限”仍可独立使用；手工追加的内容可在提交前调整或删除。
5. 最终权限范围为：锁定复制结果＋手工添加角色＋手工选择数据权限。
6. 启用/禁用表单不展示申请单号输入框；提交后系统自动生成单号并用于审批与记录。

### 验收

- 对应 `P03-01` 至 `P03-03`。

## SPEC-04：用户管理统一编辑

### 目标

降低用户列表操作列复杂度，将基本信息、角色和数据权限维护收拢到同一编辑入口。

### 业务规则

1. 用户列表删除独立的“分配数据权限”和“设置角色”操作。
2. “编辑”打开统一用户工作区，保留基本信息、角色、数据权限、历史变更和登录日志页签。
3. “详情”继续以只读模式打开相同工作区，可从详情进入编辑。
4. 启用/禁用作为独立高风险操作保留。

### 验收

- 对应 `P04-01`、`P04-02`。

## SPEC-05：数据源一级目录绑定

### 目标

数据源只绑定到一级目录/大菜单，避免每个子菜单重复维护。

### 业务规则

1. 新增和编辑数据源时，只能选择功能目录树的一级根节点。
2. 数据源保存的 `menu` 和 `group` 统一为一级目录名称。
3. 列表树、详情、筛选和权限引用均以一级目录展示。
4. 既有子菜单 mock 数据在页面初始化时归一到对应一级目录。

### 验收

- 对应 `P05-01`、`P05-02`。

## SPEC-06：三场景权限范围统一

### 6.1 目标

将以下三个业务场景中的“权限范围”收敛为同一个产品能力：

1. 内部账号首次访问工作台时，在无权限页提交首次访问申请。
2. 用户进入系统后，从“权限变更”卡片发起权限变更申请。
3. 用户进入系统后，从“创建账号”卡片为外部协作人员创建账号并配置权限范围。

三个场景以**进入系统后的现有权限范围选择**为产品和视觉基线。统一不只指按钮名称和页面外观相似，还必须统一权限目录、角色数据、复制对象数据、选择与合并规则、来源标识、提交快照和验证口径。

### 6.2 统一术语

三个场景的操作按钮固定为以下文案，不允许出现同义变体：

1. `添加角色`
2. `复制他人角色`
3. `选择数据权限`

其中“复制他人角色”是用户可见按钮文案。其业务能力固定为：复制对方当前有效的角色、由这些角色继承的功能权限与数据权限，以及用户单独授权的数据权限；不复制所属租户、组织归属和账号基本资料。用户不能脱离角色单独新增功能权限；手工添加角色时可以在该角色绑定范围内取消或恢复功能勾选，复制角色的功能权限不得调整。

### 6.3 页面结构与顺序

权限范围步骤固定按以下顺序渲染：

1. 步骤标题与说明。
2. `所属租户`多选区域。
3. 操作按钮行：`添加角色`、`复制他人角色`、`选择数据权限`。
4. 已选择权限来源区，按“手工添加角色 / 复制他人角色 / 手工选择数据权限”分组展示。
5. 字段错误、步骤操作区或提交操作区。

`所属租户`必须位于三个操作按钮上方，不得在任一场景中放到按钮下方或来源结果区之后。

### 6.4 必填与可选规则

- `所属租户`为三个场景共同的必填项，支持多选，至少选择 1 个租户。
- `添加角色`非必选。
- `复制他人角色`非必选。
- `选择数据权限`非必选。
- 三个权限入口整体也非必选，不要求三选一。
- 首次访问和创建账号场景允许只选择所属租户、不添加角色、不复制他人角色、不选择数据权限后继续提交。
- 未选择任何角色或数据权限时，页面展示中性空态，不显示错误；空态说明应明确“角色和数据权限可按需添加”，不得暗示必须选择。

### 6.5 统一选择与合并规则

#### 添加角色

- 使用系统内现有角色目录作为唯一角色源。
- 弹窗使用角色列表与详情双栏；详情保留功能权限 / 数据权限页签、分组权限树、搜索和展开收起。
- 选择角色时完整带入该角色当前绑定的功能权限和数据权限。
- 手工添加角色时默认带入角色全部功能权限，用户可在该角色绑定范围内取消或恢复勾选；勾选某项功能时自动勾选对应角色，取消功能不自动取消角色，取消角色时清理不再由其他已选或复制角色提供的功能。
- 手工添加的角色可在提交前查看详情或移除。

#### 复制他人角色

- 按 ITCode 查找可复制对象。
- 复制对方当前有效的角色，以及这些角色对应的功能权限和数据权限。
- 同时复制对方角色之外由用户单独授权的数据权限。
- 不复制任何用户单独授权、压制或调整的功能权限；有效功能权限必须严格由复制角色推导。
- 数据权限按来源展示“角色继承”或“用户单独授权”。
- 复制结果整体只读，不允许删除、局部清除、取消某一项或修改来源。
- 复制完成后不得再次复制另一个人；按钮进入明确禁用/完成状态。
- 复制结果之外仍可继续手工添加角色和选择数据权限。

#### 选择数据权限

- 使用系统内现有数据权限目录作为唯一数据源。
- 使用“一级目录 → 数据集”两层结构；一级目录默认展开，支持手动折叠、目录内搜索和多选。
- 复制带入的数据权限在选择器中保持选中和锁定，并显示来源。
- 手工选择的数据权限可在提交前调整或移除。

#### 合并规则

- 角色、功能权限、数据权限和租户均按稳定 ID 去重，展示顺序不影响最终结果。
- 最终有效功能权限为“手工角色范围内已勾选的功能 + 复制角色完整功能”的去重并集；角色范围外的直接功能 ID 必须丢弃，复制角色功能不得取消。
- 最终有效数据权限为：角色继承数据 + 复制用户单独授权数据 + 本次手工选择数据，并保留角色继承或用户单独授权来源。
- 相同权限来自多个来源时只生成一项有效权限，但保留足够的来源信息供审批详情解释。

### 6.6 三场景差异矩阵

| 场景 | 初始权限基线 | 所属租户 | 三个权限入口 | 最终提交附加校验 |
| --- | --- | --- | --- | --- |
| 首次访问 | 空权限基线 | 多选、至少 1 项 | 均非必选 | 不做新旧权限差异校验 |
| 权限变更 | 被申请人当前有效权限 | 多选、至少 1 项 | 均非必选 | 最终结果必须与初始基线不同 |
| 创建账号 | 空权限基线 | 多选、至少 1 项 | 均非必选 | 不做新旧权限差异校验 |

除上表明确列出的场景差异外，三处权限范围选择不得存在其他内容、交互、权限目录或快照结构差异。外围的基本信息字段、人员身份规则和审批链仍按各自业务场景处理，不强制统一。

### 6.7 权限变更的“无变化禁止提交”规则

该规则只适用于从`权限变更`卡片进入的申请。

#### 基线建立

- 进入权限变更流程并确定被申请人后，记录被申请人的当前有效权限快照。
- 基线至少包含：所属租户、角色 ID、最终有效功能权限 ID、最终有效数据权限 ID，以及现有模型中会影响有效结果的抑制/例外配置。
- 基线在本次表单生命周期内保持不变；用户操作过程中不得用中间状态覆盖基线。

#### 比较口径

最终提交时，对“当前表单最终权限结果”和“进入流程时的基线”做归一化、顺序无关的集合比较。以下任一最终结果发生变化，即视为有效权限变更：

- 所属租户集合发生增加或删除。
- 角色集合发生增加或删除。
- 最终有效功能权限集合发生增加或删除。
- 最终有效数据权限集合发生增加或删除。
- 其他会改变最终有效权限结果的例外或抑制配置发生变化。

以下行为不算权限变更：

- 仅打开、搜索或关闭任一选择弹窗。
- 选择后又恢复到原始权限结果。
- 只改变列表顺序或展示顺序。
- 复制操作发生过，但最终有效租户、角色、功能和数据权限与基线完全一致。
- 只改变前端临时状态、搜索关键词或展开收起状态。

#### 拦截时机与反馈

- 用户可以进入最终确认步骤；只在点击最终`提交申请`时执行无变化校验。
- 如果未检测到任何最终权限变化，禁止创建申请单、禁止写入审批列表、禁止显示提交成功。
- 在最终提交操作附近展示明确错误：`未检测到权限变更，请返回权限范围调整所属租户、角色或数据权限后再提交。`
- 错误使用 `role="alert"` 或等价可访问语义，并将焦点移到错误提示或首个可恢复操作。
- 用户点击`上一步`返回权限范围后，原有表单状态必须保留。

### 6.8 校验时机

- 所属租户在离开权限范围步骤和最终提交时均校验；未选择时在字段附近提示并阻止继续。
- 三个权限入口不做必填校验；未添加任何角色或数据权限时展示中性空态，不展示错误态。
- 权限变更的差异校验只在最终提交时执行，不因进入页面、打开弹窗或切换步骤提前报错。
- 租户、角色或权限目录仍在加载时，禁用确认或提交操作，避免以不完整数据生成快照。

### 6.9 共享组件与数据约束

三处入口必须复用同一套权限范围组件、目录数据和状态计算，不允许仅复用弹窗外观、但分别维护选择结果与校验逻辑。共享范围至少包括：

- 所属租户多选。
- 三个操作按钮及其弹窗。
- 角色、复制结果、数据权限的来源展示。
- 稳定 ID 去重、锁定与合并规则。
- 权限快照生成、归一化和差异比较。
- 加载、空数据、失败、只读、长文本和滚动状态。

推荐的共享快照语义如下；字段命名可适配现有代码，但不得丢失等价信息：

~~~ts
interface PermissionScopeSnapshot {
  tenantIds: string[]
  selectedRoleIds: string[]
  copiedFromItcode: string | null
  copiedRoleIds: string[]
  copiedDataSourceMap: Record<string, '角色继承' | '用户单独授权'>
  effectiveFunctionPermissionIds: string[]
  effectiveDataPermissionIds: string[]
  manualDataPermissionIds: string[]
}
~~~

`effectiveFunctionPermissionIds`必须限制在 `selectedRoleIds + copiedRoleIds` 对应角色的功能并集内：保留手工角色范围内已勾选的子集，并强制合入复制角色的完整功能。兼容历史申请时，角色范围外的 `copiedFunctionPermissionIds` 或其他用户级直接功能授权字段只允许读取后忽略，不得重新写入当前状态或提交载荷。

实现时应从同一状态生成页面展示、提交载荷和差异比较输入，避免三者各自计算导致结果漂移。

### 6.10 UI 与可用性规则

- 以系统内现有权限范围页面的字体、间距、圆角、控件尺寸和弹窗样式为视觉基准。
- “添加角色”作为主要操作；“复制他人角色”和“选择数据权限”使用同级弱操作样式，但三者都保持清晰可发现。
- 所属租户多选必须呈现默认、悬停、选中、聚焦、禁用和错误状态；标签与错误文案建立可访问关联。
- 每项已选结果标明来源；复制结果同时显示复制对象，并保持整体锁定。
- 弹窗具备焦点圈定、Esc 关闭、键盘可操作和明确焦点样式；内容超高时主体滚动，标题和底部操作可达。
- 审批操作弹窗内打开权限选择器时，添加角色、复制他人角色和选择数据权限必须使用统一的权限子弹窗层级，高于审批弹窗及其遮罩；关闭子弹窗不得关闭外层审批弹窗或清空审批草稿。
- 系统内页面至少验证 1440×900 和 1280×800；首次访问页额外验证 390×844 防溢出。
- 深色模式只跟随系统内页面现有支持范围；本需求不单独新增或删除深色模式能力。

### 6.11 必须覆盖的状态

- 未选择任何角色或数据权限：中性空态，允许在已选租户后继续。
- 未选择所属租户：字段级错误，阻止继续或提交。
- 角色或数据权限搜索无结果：提供清空关键词或返回目录的恢复路径。
- 复制 ITCode 为空、格式无效或查无此人：就近提示，不改变现有权限结果。
- 复制加载中：防止重复确认。
- 租户、角色或权限目录加载失败：展示可重试反馈，并保留用户已完成的其他选择。
- 租户、角色、目录或权限名称很长：文本可换行或省略，完整内容可通过标题或详情查看，不遮挡操作。

### 6.12 禁止实现

- 不允许三处使用不同按钮文案、顺序或布局。
- 不允许把任一权限入口设为必选。
- 不允许分别维护三份租户、角色或数据权限 mock/接口映射。
- 不允许只共享弹窗模板，却继续复制粘贴三份权限状态和校验逻辑。
- 不允许用“用户是否操作过”代替最终有效权限差异比较。
- 不允许无变化的权限变更申请进入审批列表。
- 不允许校验失败后清空用户已填写内容或静默无反馈。

### 6.13 Definition of Done

1. 三处权限范围由同一共享实现驱动，不再存在独立维护的业务逻辑。
2. 三处按钮文案、页面顺序、弹窗行为、来源展示和快照语义一致。
3. 所属租户均为多选且至少选 1 项；三个权限入口均非必选。
4. 权限变更无最终变化时不可提交；租户、角色或数据权限发生变化时可提交，功能权限变化只能由角色变化产生。
5. 首次访问和创建账号均可只选择租户后提交。
6. 自动化测试覆盖快照归一化与差异比较，包括顺序变化、重复 ID、选择后恢复、仅租户变化等边界。
7. typecheck、lint 和生产构建通过，且未引入新的高风险警告。
8. 在 1440×900、1280×800 完成三场景浏览器点击验证；首次访问页额外通过 390×844 防溢出检查，控制台无本次改动引入的错误。
9. docs/UI_ACCEPTANCE.md 中 P06 系列用例全部通过并留有可复验证据。

### 6.14 非目标

- 不调整基本信息字段、人员身份判断或审批链规则。
- 不调整账号启用、禁用、重置等其他申请类型。
- 不接入真实组织架构、SSO、审批引擎或权限后端。
- 不借本需求重做权限系统视觉、替换技术栈或新增生产依赖。

本 SPEC 的可执行验收用例统一记录在 docs/UI_ACCEPTANCE.md 的 P06-01 至 P06-20；2026-08-09 已补充角色内功能勾选、角色联动、历史越界功能清理、三场景复制一致性和审批嵌套弹窗层级验收。
## SPEC-07：数据权限一级目录化与目录内搜索

### 目标

数据权限的展示层级与门户工作台左侧一级目录保持一致，移除页面/二级菜单中间层，让大量生产数据集可以在所属一级目录内快速定位。功能权限目录层级不在本阶段调整范围内。

### 业务与交互规则

1. 所有数据权限选择和回显统一采用“一级目录 → 数据集”两层结构，不展示页面、二级菜单或其他中间层级；所有一级目录首次显示时默认展开，仍可手动折叠。
2. 数据集直接展示原始数据集名称，不拼接目录、类型、地域等前缀或后缀；权限稳定 ID、角色绑定和提交语义保持不变。
3. 每个一级目录标题右侧固定展示搜索图标，并提供可访问名称“搜索{一级目录名称}下的数据集”。
4. 点击搜索图标后自动展开当前一级目录并显示目录内搜索框；搜索仅过滤当前目录的数据集，各目录的关键词和开关状态互不影响。
5. 搜索按数据集名称实时模糊匹配，不改变已勾选状态；无结果时仅在当前目录内展示“暂无匹配的数据集”。
6. 清空或关闭当前目录搜索后恢复该目录全部数据集；关闭搜索时清空该目录关键词。
7. 大量数据集由弹窗或详情主体纵向滚动承载，目录标题、搜索入口和数据集名称不得挤压勾选框、来源标记或操作按钮。

### 统一范围

- 首次访问、权限变更、创建账号的“添加角色”数据权限页签。
- 首次访问、权限变更、创建账号的“选择数据权限”弹窗。
- 角色管理的新建角色、编辑角色和角色只读详情。
- 用户角色详情、用户级普通数据权限和审批只读回显中使用同一展示口径。

### 非目标

- 不调整功能权限的“一级目录 → 页面 → 功能”结构。
- 不修改数据权限 ID、复制边界、角色绑定、用户级数据例外或权限变更差异判断。
- 不调整数据源管理本身的维护字段和接口契约。

### 验收场景索引

对应 docs/UI_ACCEPTANCE.md 的 P07-01 至 P07-09。

## SPEC-08：权限申请填写信息字段规范化

### 目标

以评审确认的字段表为唯一业务口径，规范“权限申请 → 填写信息”中的权限变更（内部/外部）、创建账号、启用/禁用账号（内部/外部）五种组合，保证字段名称、顺序、必填状态、自动带出、人员类型切换、提交载荷和审批回显一致。

### 字段与交互规则

1. 五种组合的字段矩阵、顺序和必填状态以 docs/UI_SPEC.md 的 SPEC-08 为准，由同一字段 Schema 驱动页面和校验。
2. 申请人用户名与 ITCode 合并只读展示；申请人直线经理仅在权限变更和创建账号中自动带出。
3. 内部人员填写被申请人 ITCode；外部人员和创建账号填写被申请人用户名及关联人 ITCode。
4. 被申请人直线经理仅用于内部人员权限变更，必填且可编辑；启用/禁用不展示任何直线经理。
5. 手机号和邮箱始终选填，申请原因始终必填；创建账号额外要求两次密码一致。
6. 人员类型或申请类型变化时，隐藏字段不校验、不提交；提交与审批详情使用相同 Schema 过滤字段。
7. 重置密码明确排除在本次范围之外，继续使用独立身份验证流程。

## SPEC-09：用户管理资料与权限操作治理

### 目标

让系统管理员在用户管理中清晰区分“直接维护用户主档”和“发起权限变更审批”，消除手工申请单号，避免审批前权限提前生效，同时保持人员资料、租户和权限范围与权限申请口径一致。

### 业务规则

1. 用户基本信息按内部/外部人员动态展示：内部人员要求用户 ITCode 和用户直线经理；外部人员要求用户名和关联人 ITCode；手机号、邮箱选填。
2. 所属租户改为必填多选。租户属于权限范围，和角色、角色数据例外、用户单独数据授权一起比较最终有效差异。
3. 用户基本信息不展示用户显示名称、用户账号、内部 AD 账户和是否绑定 ITCode；底层用户 ID 由系统维护，新用户显示名称默认取用户名/ITCode。
4. 所属组织为非必填多选，联系方式、有效期、所属组织和备注由系统管理员直接保存；租户、角色或数据权限变化必须提交权限变更申请。
5. 用户管理的启用/禁用是系统管理员直接操作：确认后立即生效，只写审计历史，不生成审批单、不进入审批列表。
6. 权限变更不再要求填写审批单号。提交时由系统自动生成新申请单号，复用既有权限变更审批链并进入审批列表。
7. 提交审批时只保存待生效快照，用户仍使用原权限；全部审批通过后系统一次性应用租户、角色和数据权限。
8. 同一用户存在待审批的用户管理权限变更时，禁止再次修改或提交权限范围，但允许继续维护基本信息。
9. 同次编辑同时修改基本信息和权限范围时，基本信息立即保存，权限范围等待审批；审批驳回不回滚已保存的基本信息。

### 非目标

- 不改变权限申请页面中启用/禁用账号仍需审批的既有产品规则；本 SPEC 的直接启停只适用于系统管理员使用的“用户管理”。
- 不调整既有审批链节点、审批人计算、角色负责人或业务负责人规则。
- 不接入真实后端、数据库迁移或真实消息通知。
