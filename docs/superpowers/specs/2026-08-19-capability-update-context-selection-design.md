# Skill 能力更新上下文预选设计

## 背景

Skill Hub 中存在能力上下文更新时，用户点击“更新”会进入 Skill 创建的第 2 步“需求澄清”。当前更新草稿已经记录受影响的能力编码，但当 Skill 创建页签此前已打开时，组件不会重新挂载，路由变化没有触发草稿恢复，页面仍显示“新建 Skill”和“0 已选”。

## 已确认规则

- 点击“更新”或“继续更新”后直接进入 Skill 创建第 2 步。
- 自动勾选本次能力更新中 `currentContextCodes` 指向的受影响能力上下文。
- 已有草稿中的其他已选能力继续保留，不因本次更新被清空。
- 新增但尚未选择的独立能力仍显示为“可选新增”，不自动勾选。
- 当前线上 Skill 继续生效；本次调整只影响编辑草稿。

## 方案选择

### 方案 A：监听路由并恢复更新草稿（采用）

Skill 创建页监听 `skill`、`edit`、`capabilityUpdate` 查询参数。参数变化时重新读取 sessionStorage 或 Skill Hub store，并恢复表单、能力上下文和第 2 步状态。创建能力更新草稿时，将原草稿选择与 `currentContextCodes` 做并集。

优点：覆盖“页签已打开”和“首次进入”两种场景；保持现有路由和页签结构；改动范围小。

### 方案 B：强制销毁并重建 Skill 创建页

为路由视图增加动态 key，让查询参数变化时重建整个页面。

缺点：会重置页面内未保存状态，影响普通创建和编辑流程，范围过大。

### 方案 C：把预选编码全部写入 URL

Skill Hub 跳转时把受影响能力编码拼入查询参数，Skill 创建页按 URL 初始化。

缺点：与现有草稿数据形成两个事实来源，容易产生参数过期和选择覆盖问题。

## 数据流

1. 用户在 Skill Hub 点击“更新”。
2. `startCapabilityUpdate` 创建或复用编辑草稿，并将草稿已有选择与 `currentContextCodes` 合并去重。
3. Skill Hub 写入 sessionStorage，跳转到 `/agent/skill-create?skill=...&edit=draft&capabilityUpdate=1`。
4. Skill 创建页首次挂载或路由参数变化时执行同一套恢复逻辑。
5. 页面切换到第 2 步，左侧能力目录和中间“已选择”区域同步显示勾选结果。
6. `contextId` 对应的可选新增能力只有用户点击“加入上下文”后才进入已选列表。

## 边界与异常

- sessionStorage 不存在或与当前 skill 不匹配时，从 Skill Hub store 恢复。
- 找不到目标 Skill 时沿用当前页面状态，不清空用户未保存内容。
- 重复进入同一能力更新时保持幂等，不重复追加能力编码。
- 普通“创建 Skill”“编辑”“驳回后修改”不执行能力更新预选逻辑。

## 验证

- 无既有草稿：点击“更新”后进入第 2 步，并选中全部 `currentContextCodes`。
- 有既有草稿：保留原选择，同时补选本次受影响能力。
- Skill 创建页签已打开：从 Skill Hub 再次点击“更新”仍能刷新为目标 Skill，而不是显示“新建 Skill”。
- “可选新增”保持未选，手动加入后才进入已选列表。
- “继续更新”恢复当前草稿，不丢失用户编辑内容。
- 现有创建、编辑、驳回修改、评估和提交审核回归通过。
