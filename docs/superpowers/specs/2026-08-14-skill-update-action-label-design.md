# Skill Hub 更新按钮状态设计

## 目标

能力变化首次出现时，Skill Hub 操作显示“更新”。只有用户在能力更新流程中形成并保存有效编辑草稿后，返回 Skill Hub 才显示“继续更新”。

## 状态规则

- 能力变化为可处理状态，但尚未保存编辑：显示“更新”。
- 仅打开能力更新页后直接返回：仍显示“更新”。
- 在能力更新页成功保存草稿：显示“继续更新”。
- 更新版本已提交审核、被驳回后继续修改等已有编辑阶段：显示“继续更新”。
- 能力更新发布完成并进入 resolved：不再显示更新操作。

列表操作与“能力变化详情”弹窗必须使用同一个文案判断函数。

## 数据设计

在 `SkillCapabilityUpdate` 上增加可持久化的布尔标记 `hasDraftEdits`：

- 新发现的变化及首次打开更新页时为 `false`。
- `mergeCapabilityDraft` 和 `mergeCapabilitySubmission` 成功写入草稿时设为 `true`。
- 旧缓存没有该字段时按 `false` 兼容，避免仅因历史 `processing` 状态显示“继续更新”。
- 发布更新后能力记录进入 `resolved`，沿用现有收口逻辑。

## 交互与兼容

- `processing` 继续表示更新流程已被打开，用于加载能力上下文和保留线上版本，不再直接决定按钮文案。
- 新增纯函数判断按钮文案，列表和详情弹窗共同调用。
- 不改变“查看变化”、审批、驳回、发布、禁用及右侧 Agent 行为。
- 不改变正式环境、公共导航和其他 Skill 的编辑逻辑。

## 验证

- 首次 `beginCapabilityUpdate` 后文案仍为“更新”。
- 保存能力更新草稿后文案变为“继续更新”。
- 提交更新版本后文案保持“继续更新”。
- 列表与详情弹窗调用同一判断函数。
- 现有能力更新测试、lint、typecheck、build 和页面烟测通过。
