# 权限系统 POC UI Spec

版本：v1.0
更新日期：2026-08-07
页面范围：登录页、无权限页、权限申请、审批列表/详情、用户管理、数据源管理。

## 1. 目标与非目标

- 目标：将账号创建与权限申请合并，让内部用户在无权限错误页内完成首次访问申请，按人员身份生成正确审批链路，并降低申请人和管理员的操作复杂度。
- 目标用户：内部申请人、外部申请人、关联人、直线经理、业务负责人、系统管理员。
- 核心任务：首次访问申请、外部账号创建并授权、权限变更审批、用户权限维护、数据源绑定。
- 非目标：本期不接真实组织架构、SSO、审批引擎或数据源接口；POC 继续使用前端 mock 数据。
- 非目标：不重做权限后台视觉风格，不引入新的组件库或生产依赖。

## 2. 视觉与交互依据

优先级如下：

1. 本轮评审结论和用户确认的审批规则。
2. 当前 Vue POC 已有页面、组件、颜色和间距体系。
3. `docs/portal-workbench-permission-design.md` 中的权限分层原则。
4. 全局《Codex 前端 UI 开发协作 STD》。

项目规则引用的 `/opt/projects/lexiang/.codex/skills/lenovo-leai-pc-design/SKILL.md` 未包含在当前 Windows 工作副本中。本轮仅复用现有视觉，不新增品牌表达；最终仍需在具备该规范的环境中复核。

## 3. 平台与布局

- 高保真目标：PC 管理后台，主要验证 1440×900。
- 最小支持宽度：1024px；小于该宽度以不遮挡、不丢失关键操作为目标。
- 登录页和无权限页继续支持现有移动端防溢出布局。
- 页面级滚动沿用现有工作台；弹窗内容超高时由弹窗主体滚动。

## 4. 通用交互规则

- 人员类型决定字段和审批节点：外部用户永远不展示“被申请人直线经理”。
- 多个业务负责人必须全部通过，权限才一次性整体生效。
- 申请人最终提交页只展示审批流，不展示复杂权限变更摘要。
- 权限变更摘要只在审批列表或审批详情中展示。
- 启用/禁用申请单号由提交后自动生成，表单中不要求手填。
- 复制权限与手工追加权限分区展示，来源清楚且互不混淆。
- 表单校验在字段附近展示；提交失败不得静默。

## 5. 关键组件状态

| 组件 | 默认状态 | 禁用/只读 | 错误/空状态 |
| --- | --- | --- | --- |
| 无权限错误页 | 原页展示基本信息、权限范围和提交申请三步流程 | 已有待审批申请时显示原申请结果，避免重复提交 | 无 ITCode 时使用安全占位；保存失败时留在原页提示 |
| 权限范围 | 展示角色、复制结果、数据权限三种来源 | 复制结果整体锁定 | 无权限时展示明确空态 |
| 审批流 | 按身份动态生成节点 | 已完成节点只读 | 缺审批人时展示“待带出” |
| 审批详情摘要 | 展示新增、移除和来源变化 | 申请信息只读 | 无变化时展示“未检测到变化” |
| 用户编辑 | 基础信息、角色、数据权限统一入口 | 详情模式全部只读 | 保存错误定位到对应页签 |
| 数据源绑定 | 仅选择一级目录/大菜单 | 子菜单不可选 | 未选择一级目录时阻止保存 |

## 6. 禁止项

- 不为外部用户生成直线经理字段或审批节点。
- 不允许修改、删除或局部清除“复制他人权限”带入的任何权限。
- 不允许业务负责人部分通过时提前生效部分权限。
- 不把系统管理员放在普通权限变更的最终审批节点。
- 不继续保留外部登录页自助创建账号入口。
- 不允许内部首次访问申请从无权限错误页跳转到后台权限管理页面。
- 不在用户列表操作列同时保留“编辑”“设置角色”“分配数据权限”三个入口。

## 7. 技术约束与验证

- 框架：Vue 3、Vue Router、Pinia、TypeScript、Vite。
- 样式：继续使用组件内 scoped CSS 和现有 class，不增加无边界全局覆盖。
- 数据：沿用 localStorage 和页面内 mock 状态，保持邮件 mock 可演示。
- 基础验证：`pnpm run typecheck`、`pnpm run lint`、`pnpm run build`。
- 浏览器验证：按 `docs/UI_ACCEPTANCE.md` 覆盖 1440×900 的主要身份和流程。
